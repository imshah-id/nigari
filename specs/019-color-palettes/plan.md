# Implementation Plan: Named colour palettes, and role tokens that reference them

**Branch**: `claude/spec-019-palettes` (spec and plan); the build gets its own branch | **Date**: 2026-11-17 | **Spec**: [spec.md](spec.md) | **Issue**: #379 (spec 020 builds on this)

**Input**: Feature specification from `/specs/019-color-palettes/spec.md`

## Summary

Colours move to three tiers: **named palettes** (one OKLCH base each, the
steps generated by a relative change in lightness), **role tokens**
(`primary`, `primary-pressed`, `destructive`, neutral and data roles) that
each reference a palette step per theme, and a **flat** `tokens.css` of
role variables. Swapping a role's colour is one edit; the contrast checks
run on the result.

- **Generation**: one fraction table for every palette, fitted to where
  today's colours sit (R1); dark mode takes the nearest step (owner).
- **Tiers and names**: palettes `raspberry`, `burnt-orange`, `stone`,
  `slate` and one per data hue; roles by what they do (R2, R5).
- **Nothing visible changes** beyond the nearest-step differences: every
  CSS variable the stylesheets read today stays, as an alias of its role
  (R2). No stylesheet or component changes in this spec.
- **Guard**: components may not read a palette step (R4).

One pull request. Spec 020 (the button) starts after it merges.

## Technical Context

**Language/Version**: Node (the token build, `web/scripts/build-tokens.mjs`); CSS custom properties

**Primary Dependencies**: none new. The build's own OKLCH conversion.

**Storage**: none. Select options keep the colours they store (R5).

**Testing**:
- `check-build-tokens.mjs`: new cases for generation, references, a swap
  failing contrast, and a palette name refused outside `tokens.css`.
- `build-tokens.mjs --check`: the committed `tokens.css` is what the
  tokens build.
- `check-chartcolours.mjs` on the renamed data roles; the 3:1 rule.
- A before/after table of every role's colour (both themes) in the pull
  request; the wiki screenshots retaken and compared.

**Target Platform**: the browser, light and dark; the desktop shell

**Performance Goals**: N/A (build time only)

**Constraints**: design system ratchets only go down; English source

**Scale/Scope**: 1 PR; 4 interface palettes + 13 data palettes; about 70
role tokens (today's semantic tier has 70 values); 0 stylesheet changes.

  OPTION_TOKEN"`: `oklchToSrgb` has one caller (the build); the contrast

  `OPTION_TOKEN` (two callers, `chartTheme.ts`) maps stored option hexes
  to chart tokens.
- `codegraph callers groupColourTokens` → `ChartFigure` and
  `check-chartcolours.mjs`: the chart's colour choice is checked by name,
  so the data roles' names flow into that check.
- Not from the graph (CSS is not indexed): the stylesheets read the
  legacy names far more than the token names (`--muted` 223, `--border`
  166, `--fg` 106, `--accent` 103, `--hover` 91, `--accent-rgb` 50, …;
  `--color-*` names 6–36 each), so the aliases must stay (R2).
- `OPTION_HEXES` (`selectOptions.ts`) are stored in users' schemas: data,
  not tokens (R5).

**New concepts**: the design system's colour tiers. Added to
`.specify/memory/surfaces.md` under Design system: "a colour is a role token
(`--color-primary`, `--color-data-3`); a role references a named palette's
step per theme; components never read a palette (`--palette-*`, refused by
`check-tokens.mjs`); a new colour need is a new role, not a new value."

**Parity statement**: No agent capability: colours are how the interface
draws; nothing an agent can or cannot do changes.
